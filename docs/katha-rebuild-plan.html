Rebuilding SnapReels as Katha on FastAPI, Postgres, Next.js and React Native

A feature-by-feature reading of the purchased SnapReels v1.1.7 package, the architecture that replaces it, and the mobile platform decision.

Source: SnapReels 1.1.7 (web) + Android 1.1.6 Target bundle: com.mobirizer.katha Prepared 2026-09-07

Verdict

Three conclusions that shape everything below.

The package

Use it as a spec, not a codebase

SnapReels is a Firebase Studio prototype that was migrated to MongoDB. The product surface is complete and worth copying. The backend trusts the client for coins, unlocks and payments, so none of its server code should ship.

The stack

Thin clients, one FastAPI core

Next.js web and admin, plus a React Native app, all talk to one FastAPI service over a generated OpenAPI client. Postgres holds a coin ledger instead of a mutable balance. Video never transits the API server.

Mobile

React Native with Expo, native modules where it counts

One TypeScript codebase gives you Android and iOS on day one, which the vendor never shipped. Player, billing and ads sit on native-backed libraries. Go native only if DRM with offline downloads becomes a hard requirement.

What SnapReels really is

The listing says "SaaS script with Android app". The code says something more specific.

Web and API are one Next.js 15 app. Pages call server actions that read and write MongoDB directly. Firebase is used only for end-user sign-in. The admin panel is a single hard-coded account with an encrypted cookie. A handful of REST routes under /api/mobile/v1 and /api/user exist for the Android app, guarded by one shared static API key.

The Android app is native Kotlin with Jetpack Compose, Media3 ExoPlayer, Room, and hand-rolled JSON parsing over OkHttp. It ships Google Play Billing, AdMob, AppLovin MAX and Facebook Audience Network, with a round-robin ad rotation. The package name is still com.example and the manifest carries Google's test AdMob app ID.

The AI features are a single "generate metadata from a seed sentence" button and a bulk UI translation action, both calling Groq, OpenAI or Gemini with admin-entered keys. The Genkit flows in the source tree are dead scaffolding that nothing imports.

Video is served by proxying MP4 files through the Node process with an AES-encrypted, time-bucketed token. HLS URLs bypass the proxy entirely. There is no transcoding, no per-user token, and locked episodes' URLs are sent to every client.

What not to carry over

These are the reasons the vendor backend is a spec rather than a starting point.

Security holes that Katha must close by design

  • Every coin mutation trusts the client. Unlock, claim reward, daily check-in, favourites, history and purchase verification are server actions that take a user id from the request and never check a session. Anyone can mint coins for any account.
  • Unlock price comes from the payload. The web unlock action deducts whatever cost the browser sends, and spreads the raw payload into the database.
  • Payments have no webhooks and no binding. Verification only compares the amount, so a paid session for one pack redeems any pack of the same price, and the first account to present someone else's session id wins.
  • Google Play purchases are never acknowledged, the app sends the order id where the server expects the purchase token, and subscriptions are checked against the products endpoint. Real purchases would be auto-refunded after three days.
  • Locked episodes leak their video URLs. Both the web page payload and the mobile episodes endpoint return playable proxy links for premium episodes. The lock is UI only.
  • One static API key in the APK, extractable because release builds are not minified, is the only guard on unlock, claim, checkout and library endpoints.
  • Rewarded ads and link timers are client-attested. No server-side verification from any ad network.
  • All third-party secrets live in MongoDB and are returned in full by settings readers that client components import. A full-database export action exists with no session check.
  • Admin mutations do not verify the session; they rely on the page being behind middleware that only regex-checks the cookie shape.

Dead weight to leave behind

  • The license phone-home to the vendor's server, the install wizard, and the "any string over 10 characters activates" test action.
  • Firestore client, rules and hooks, Genkit flows, App Hosting config and the on-device Gemini service with an empty key. All unused.
  • The Node video proxy, the global removeChild monkey-patch, the JSON backup and restore, the Trending and iOS placeholder pages, the duplicate unrouted episodes page.
  • Client-side pagination of the whole catalogue and user list, the two different "likes" collections, and the hard-coded dark theme with lang="en" on every locale.

Unlock in one transaction

Load episode and series with the user's active VIP row. Reject if not free, not VIP, and the previous episode is not unlocked. Insert the ledger row with delta = -price and an idempotency key of unlock:{user}:{episode}. Update the balance with a coin_balance >= price guard. Insert the unlock row. Commit. The mobile client's "auto-unlock next" simply calls the same endpoint.

Video pipeline

The single largest upgrade over the package, and the one that decides hosting cost.

  1. Upload. Admin gets a presigned PUT URL from the API and uploads straight to the bucket. The API records a video asset in uploaded state.
  2. Transcode. The worker runs ffmpeg into an HLS ladder of 1080p, 720p and 480p portrait renditions, generates a poster and a sprite sheet for seeking, and writes the master playlist. Status moves to ready and the episode becomes publishable.
  3. Serve. Clients ask POST /v1/episodes/{id}/play. The API checks access, then mints a CDN signed URL or signed cookie valid for a few minutes, scoped to that episode's path. CloudFront, Bunny and Cloudflare all support this natively.
  4. Protect. Renditions are AES-128 encrypted with keys served by the API behind the same access check. This is not DRM, but it means a shared m3u8 link is useless without a session. Widevine and FairPlay can be added later through a packager such as Shaka if downloads or studio content require it.
  5. Preload. Because the URL is per-episode and short-lived, the mobile app requests play tokens for N and N+1 together, and the API returns both when N+1 is already accessible.
Managed alternative for the first release

Bunny Stream, Cloudflare Stream or Mux do steps 2 through 4 as a service with token authentication and their own players. For a first release with a small team this removes the ffmpeg worker entirely. The API contract stays the same, so self-hosting later is a worker swap, not a client change.

Payments and in-app purchases

The vendor supports many gateways badly. Katha supports fewer, correctly.

ChannelMechanismLedger entry created by
Web, cards and walletsStripe Checkout with the pack id and user id in metadatacheckout.session.completed webhook, signature verified
Web, IndiaRazorpay Orders API, Checkout.js on the page, UPI includedpayment.captured webhook, HMAC verified, order id matched to the pending purchase
AndroidGoogle Play Billing through RevenueCat, coin packs as consumables, VIP as subscriptionRevenueCat webhook, purchase acknowledged and consumed by the SDK
iOSStoreKit 2 through RevenueCat, same productsRevenueCat webhook
PayPal, FlutterwaveOptional adapters behind the same purchase interfaceTheir webhooks

Every purchase starts as a pending row created by the API before the client is redirected or the store sheet opens. Webhooks flip it to paid and write the ledger entry in the same transaction. The client only polls the purchase status, it never claims success. Refund events reverse the ledger with a negative entry rather than editing history.

Direct verification against the Google Play Developer API and the App Store Server API is possible instead of RevenueCat and saves its fee, at the cost of owning acknowledgement, subscription renewals and grace periods yourself. RevenueCat is the recommendation until store revenue justifies the work.

AI layer with LangChain and LangGraph

SnapReels has one prompt button. Katha gets four graphs that run in the worker, each with a human checkpoint where money or public text is involved.

Provider strategy. A registry maps each graph to a LangChain chat model from admin settings. Claude Opus 5 through langchain-anthropic is the default for metadata, translation and moderation because of structured output quality and long context for whole-transcript work. OpenAI, Gemini and Groq stay selectable, which preserves the admin freedom the vendor offered. Embeddings use a dedicated embedding model, not the chat model.

Operational shape. Graph state is checkpointed in Postgres with the LangGraph Postgres saver, so an approval can wait for days and resume. Every run is a job row visible in admin with cost, tokens and the diff it proposes. Prompt and model changes are evaluated against a small fixed set of series before rollout.

A support assistant over reports and mailbox is a plausible fifth graph, but not for the first release.

React Native or native

The question is not whether React Native can do this. It is whether the three hard subsystems have native-backed libraries you can trust.

Recommended

React Native with Expo

  • One TypeScript codebase for Android and iOS; the vendor never shipped iOS.
  • Shares the generated API client, i18n bundle, design tokens and validation with the Next.js apps.
  • expo-video wraps ExoPlayer and AVPlayer: HLS, PiP, background audio, multiple preloaded player instances.
  • react-native-purchases (RevenueCat) handles acknowledgement, consumption and subscriptions that the Kotlin app got wrong.
  • react-native-google-mobile-ads supports rewarded ads with server-side verification. AppLovin MAX has an official RN SDK.
  • EAS Update ships JavaScript fixes without a store review. EAS Build produces both binaries from CI.
  • Expo Modules let you write Kotlin or Swift for any piece that needs it without leaving the RN shell.
When native wins

Kotlin Compose and SwiftUI

  • Hard requirement for Widevine L1 and FairPlay with persistent offline licences. Possible in react-native-video, but far better supported natively.
  • Ad mediation waterfalls across three or more networks as a primary revenue line, where SDK maturity matters more than shared code.
  • An existing team of Kotlin and Swift engineers and no TypeScript bench.
  • Two codebases, two release trains, and no iOS until it is written.

Risks to manage in React Native, with the mitigation

  • Memory in the vertical feed. Keep a window of three mounted players, release the rest, and preload only N+1. This is the same discipline the Kotlin app needed.
  • Low-end Android in India. Hermes plus the New Architecture, FlashList for rails, image caching, and a performance budget measured on a 2 GB device in CI.
  • Checkout in a WebView. Do not. Use RevenueCat for store purchases and Razorpay or Stripe native SDKs only if web checkout is ever needed in-app.
  • Native library drift. Pin Expo SDK per release, upgrade on a schedule, and keep native customisations in Expo Modules under your own package so they survive upgrades.
Identifiers

Android application id and iOS bundle id com.mobirizer.katha, with com.mobirizer.katha.dev and com.mobirizer.katha.staging variants so all three install side by side. Deep link scheme katha:// and universal links on the production domain for referrals and share.

  • Platforms. Web PWA with offline shell, TV apps if the catalogue justifies them, and a creator or partner portal for studios uploading their own series.
Shapes the schema in phase 0, even though it ships in phase 4
  • Experiment assignments. Every config response carries the user's variant map, and every ledger row, unlock and analytics event records the variant it happened under. Adding this later means re-keying history.
  • Regional pricing. Packs have a price table keyed by currency and country from day one, not a single price.
  • Playback events. The events table has a stable shape for QoE beacons so the phase 4 tuning has months of data waiting.
  • Territory and windows on series. Nullable columns now, enforced later, so licensed content never needs a migration.

Decisions to confirm

Each of these has a recommended default, so work can start without waiting. Change any of them and the plan adjusts, not the architecture.

  1. Identity provider. Default: keep Firebase Auth for Google, Apple and phone OTP, and exchange for Katha tokens. Alternative: own auth with an SMS provider such as MSG91, which costs a week and removes the Firebase dependency.
  2. Video hosting. Default: managed (Bunny Stream or Cloudflare Stream) for the first release, self-hosted ffmpeg worker on S3 plus CDN when volume or cost says so.
  3. Store purchases. Default: RevenueCat. Alternative: direct Google Play and App Store server APIs once store revenue justifies owning renewals.
  4. Launch markets and currencies. The name suggests India first, which puts Razorpay with UPI and INR pack pricing in phase 1 and makes low-end Android performance a release gate.
  5. Ad networks. Default: AdMob only at launch, AppLovin MAX second. Facebook Audience Network deferred because its React Native support is weak and its rewarded verification is not comparable.
  6. Reusing the purchased UI. The shadcn component styling and page compositions are fine to reuse under the CodeCanyon licence you hold. Confirm the licence tier covers charging end users, since the coin store does exactly that.
